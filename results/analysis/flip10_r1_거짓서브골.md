## 1. 무엇을 확인하려 했나

screen57(120분)에서 실패한 40문제의 depth-0 서브골 닫힘 비율을 재보니,
80~90%를 닫고도 실패한 문제가 8개 있었다. "서브골 하나만 남았으니 조금만
더 하면 된다"고 보고, 그 8개에 과거 성공 이력이 있는 2개를 더해 360분으로
다시 돌렸다.

결과는 2/10 이었고, **닫힘 비율 최상위였던 문제들이 그대로 실패했다.**

    algebra_cubrtrp1oncubrtreq3_rcubp1onrcubeq5778   9/10 닫음 → 360분·115시도 실패
    algebra_apbmpcneq0_aeq0anbeq0anceq0              8/9  닫음 → 360분· 87시도 실패

닫힘 비율은 갈림을 예측하지 못했다. 그래서 "왜 마지막 하나가 안 닫혔나"를
Lean 으로 직접 검증했다.

## 2. 검증 방법

flip10 r1 로그의 `PROOF PROGRESS TREE` 를 파싱해 문제별 최선 트리를 고르고,
그 안에서 ✅ 가 아닌 depth-0 서브골의 정리문을 추출했다. 각 정리문을
Lean v4.16 + mathlib 에 그대로 넣어 참/거짓을 판정했다.
검증 스크립트는 `AsyncLeanVerifier`(포트 10001) 를 직접 호출했다.

## 3. 결과 — 다섯 문제 모두 닫힐 수 없는 서브골이었다

### 3.1 `mathd_algebra_158` — 큰 연산자의 결합 우선순위

스케치가 만든 서브골:

    hS₁ : (∑ k ∈ Finset.range 8, 2 * k + 1) = 64

Lean 의 `∑ x ∈ s, body` 는 body 를 `+` 보다 높은 우선순위로 파싱한다.
따라서 위 식은 `(∑ k ∈ range 8, 2*k) + 1` = 56 + 1 = **57** 로 읽힌다.

검증:

    (∑ k ∈ Finset.range 8, 2 * k + 1) = 57      ✅ 통과
    (∑ k ∈ Finset.range 8, (2 * k + 1)) = 64    ✅ 통과   ← 괄호를 씌우면 의도대로

모델은 Σ(2k+1)=64 를 의도했으나 Lean 은 (Σ2k)+1=57 로 받았다. 서브골은
`57 = 64` 라는 거짓 명제가 됐다. 그래서 스케치를 130번 갈아치워도
닫히지 않았다.

### 3.2 `mathd_numbertheory_343` — 같은 원인 (`∏`)

    h_mod : (∏ k ∈ Finset.range 6, 2 * k + 1) ≡ (1 * 3 * 5 * 7 * 9 * 1) [MOD 10]

`decide` 판정: **proved that the proposition is false**.
좌변이 `(∏ k ∈ range 6, 2*k) + 1` 로 읽히고 ∏2k = 0 이므로 좌변은 1 이 된다.
우변 945 와 mod 10 에서 일치하지 않는다.

### 3.3 `aime_1984_p7` — 산술 오류

    h997 : f 997 = 997

가설은 n ≥ 1000 에서 f n = n - 3, n < 1000 에서 f n = f (f (n+5)) 이다.
f(997) = f(f(1002)) = f(999) = f(f(1004)) = f(1001) = 998.

검증:

    f 997 = 998   ✅ 통과
    f 997 = 997   ❌ 실패 (omega could not prove the goal)

AIME 1984 P7 의 알려진 성질은 n < 1000 에서 n 이 홀수면 998, 짝수면 997 이다.
997 은 홀수이므로 998 이 맞다. 스케치가 문제의 최종 답 997 을 중간 단계에
그대로 옮겨 쓰면서 값을 혼동했다.

### 3.4 `algebra_cubrtrp1oncubrtreq3_rcubp1onrcubeq5778` — 가설 누락

    h_pow_eq (r : ℝ) : r ^ (3:ℝ) = (r ^ ((1:ℝ)/3)) ^ (9:ℝ)

`0 < r` 가설이 없다. 실수 거듭제곱 `Real.rpow` 는 음수 밑에서 이 항등식을
만족하지 않는다(복소 주분지를 거치므로). 원 문제에는 r 에 대한 양수 조건이
있었으나 분해 과정에서 서브골로 전달되지 않았다.

이 문제는 9/10 을 트리 7개로 닫은 최유망 후보였는데, 남은 하나가 이것이었다.

### 3.5 `aime_1994_p3` — ∀ 가설을 단일 사례로 좁힌 뒤 재일반화

    hrec (x : ℤ) (f : ℤ → ℤ) (h0 : f x + f (x-1) = x^2) (h1 : f 19 = 94) :
        ∀ n : ℤ, f n + f (n-1) = n^2

`h0` 는 정리 서명에서 고정된 하나의 `x` 에 대한 가정이다. 거기서 모든 `n` 에
대한 결론은 나오지 않는다. 원 문제의 가설은 `∀ x` 였는데, 분해하면서 특정
`x` 로 좁혀놓고 그것을 다시 일반화하려 했다. 증명 불가다.

## 5. 연구에 갖는 의미

### 5.1 서브골 단위 국소 수리로는 고칠 수 없다

거짓 서브골에는 어떤 전술을 붓거나 재귀로 더 분해해도 닫히지 않는다.
스케치 자체를 폐기하고 다시 세워야 한다. 이는 "실패한 서브골을 국소적으로
수리한다"는 접근과 "스케치를 평가해 좋은 쪽으로 유도한다"는 접근 중 후자가
필요하다는 직접적인 근거다.

### 5.2 현재 스케치 검증은 컴파일 가능성만 본다

`HILBERTWorker.verify_and_correct_proof_sketch_with_theorems` (1733행) 는
스케치가 컴파일되는지만 확인한다. `have h : 57 = 64 := by sorry` 는 문법적으로
완벽하므로 통과한다. 여기가 개입 지점이다.

### 5.3 자동 반증의 실측 적용 범위 — 5건 중 2건

`scripts/verify_subgoal_truth.py` 로 위 6개 정리문을 판정한 결과:

    ❌ 거짓    hS₁_mathd_algebra_158            (decide)
    ·  보류    hS₂_mathd_algebra_158
    ❌ 거짓    h_mod_mathd_numbertheory_343     (decide)
    ·  보류    h997_aime_1984_p7
    ·  보류    h_pow_eq_algebra_cubrtr
    ·  보류    hrec_aime_1994_p3

`decide` 로 즉시 반증되는 것은 **표기 우선순위 유형 2건뿐**이다. 나머지는
자동 반증에 걸리지 않는다. 이유가 각각 다르다.

  - `h997` — 거짓이지만 반증에 가설 인스턴스화가 필요하다. 실제로는
    `f 997 = 998` 을 증명해 거짓임을 확인했으나, 그 대안값을 어디서
    가져올지가 자동화의 난점이다.
  - `h_pow_eq` — 반례(r = -8)를 제시해야 하고, `decide` 로는 실수 영역을
    판정할 수 없다.
  - `hrec` — 거짓이 아니라 **도출 불가**다. 명제 자체는 반증 대상이 아니고,
    가설이 결론을 함의하지 않는다는 구조적 문제다.

즉 반증 시도만으로는 부족하고, 아래 구조적 검사가 함께 필요하다.

### 5.4 넣을 수 있는 검사 세 가지

스케치를 만든 직후 각 서브골에 대해:

1. **반증 시도** — `decide` / `norm_num` 으로 거짓임을 보일 수 있는가.
   실측으로 3.1 · 3.2 가 걸린다(5건 중 2건). 비용은 서브골당 Lean 호출 1회다.
2. **가설 누락 검사** — 부모의 가설 중 서브골 서명에서 사라진 것이 있는가.
   3.4 가 걸린다.
3. **자유변수 검사** — 부모에 있던 `∀` 가설이 서브골에서 단일 사례로
   좁혀졌는가. 3.5 가 걸린다.

### 5.5 표기 문제는 기계적으로 수정 가능하다

3.1 · 3.2 는 `∑` / `∏` 본문에 괄호가 없고 `+` 또는 `-` 가 있을 때 발생한다.
검출하고 괄호를 씌운 변형을 함께 시도하면 된다. `mathd_algebra_158` 은
그것만으로 풀릴 가능성이 있다. 이 문제는 265분과 143회 시도를 여기에 썼다.
