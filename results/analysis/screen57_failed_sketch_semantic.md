## 1. 원 정리 자체가 거짓인 경우

### `algebra_ineq_nto1onlt2m1on`

정리에는 `n ≥ 2` 가정이 없다.

```lean
theorem algebra_ineq_nto1onlt2m1on (n : ℕ) :
    (n : ℝ) ^ ((1 : ℝ) / n) < 2 - 1 / n := by
```

`n = 1`이면 양변은 각각 1이므로 결론은 `1 < 1`이 된다. 생성된 스케치는 이를
고치지 못하고 다음과 같이 거짓인 경우 정리를 명시했다.

```lean
have h_one : n = 1 →
    (n : ℝ) ^ ((1 : ℝ) / n) < 2 - 1 / n := by sorry
```

이 문제에서 스케치 재생성은 해결책이 될 수 없다. 데이터 정리문에 `2 ≤ n`을 추가해야
한다. 실제로 후반 재귀 스케치는 이 가정을 가진 정리로 바뀌었지만, 그것은 원 정리의
증명이 아니라 반례를 제거한 별도 정리다.

### `amc12a_2020_p10`

원 정리는 `0 < n`만 가정하며 `n = 1`을 허용한다. mathlib에서 `Real.log 0 = 0`으로
정의되므로 `n = 1`일 때 주어진 로그 등식의 양변은 0이다. 그러나 1의 십진 자릿수 합은
13이 아니다.

첫 스케치는 `0 < n`만으로 로그 값이 0인 경우를 배제하려 했다.

```lean
have h_cases : Real.logb 4 (n : ℝ) = 0 ∨ Real.logb 4 (n : ℝ) = 4 := by sorry
have h_log4_n : Real.logb 4 (n : ℝ) = 4 := by sorry
```

두 번째 스케치는 정리문에 `(h₂ : n ≠ 1)`을 새로 넣었다. 수학적 결함을 감지한 흔적으로
볼 수 있지만, 원래 가정에서 도출하지 않고 문제를 변경했다. 이 문제도 스케치 품질 실험
표본보다 정리문 오류 표본으로 분리해야 한다.

## 2. 정수와 자연수 변환의 의미가 어긋난 경우

### `imo_1992_p1`

스케치는 양의 정수 `p - 1`을 자연수로 옮기면서 `.toNat.succ`를 사용했다.

```lean
((p - 1 : ℤ).toNat.succ : ℚ)
```

가정상 `p > 1`이므로 이 값은 `p - 1`이 아니라 `p`다. 그런데 스케치는 이 항을
`p - 1`처럼 해석하여 역수 부등식과 패턴 분류를 전개했다. 두 번의 생성에서 패턴도
서로 달랐다.

```lean
-- 첫 생성
(..., ..., ...) = (1, 3, 7) ∨ (..., ..., ...) = (2, 4, 14)

-- 다음 생성
(..., ..., ...) = (2, 4, 8) ∨ (..., ..., ...) = (3, 5, 15)
```

두 번째 생성은 `.toNat.succ` 삼중항이 곧 `(p,q,r)`임에도, 그 다음 단계에서 다시
`p,q,r`로 번역한다고 선언한다. 즉 증명 전략 이전에 표현의 의미가 한 칸 이동했다.
`ADEInequality.Admissible`을 이용한 분류 역시 필요한 연결 정리를 제시하지 않은 채
결론 패턴을 직접 서브골로 만들었다.

## 3. 거짓 부등식을 핵심 연결 고리로 쓴 경우

### `imosl_2007_algebra_p6`

첫 두 스케치는 다음 점별 부등식을 사용했다.

```lean
have h_refine_term : ∀ i : ℕ,
    a i ^ 2 * a (i + 1) ≤ (a i ^ 2 + a (i + 1) ^ 2) / 4 := by sorry
```

`a i = a (i+1) = 1`을 대입하면 `1 ≤ 1/2`가 되어 거짓이다. 또한 다음 Cauchy 단계는
`range 100`에서 `a (x+2)`를 사용하여 `x=99`일 때 `a 101`을 포함한다.

```lean
have h_cauchy :
    (∑ x in Finset.range 100, a (x + 1) * a (x + 2)) ≤ 1 := by sorry
```

가정은 `a 1`부터 `a 100`의 제곱합만 제한하므로 `a 101`은 임의로 크게 잡을 수 있다.
따라서 이 명제도 거짓이다.

세 번째 스케치는 점별 부등식을 참인 형태

```lean
a i ^ 2 * a (i + 1) ≤ (a i ^ 3 + a (i + 1) ^ 3) / 2
```

로 바꿨지만, 여전히 `h_cauchy`를 유지했고 `h_half : LHS ≤ 1/2`에서 더 강한
`h_final : LHS < 12/25`를 별도 서브골로 재진술했다. `1/2 > 12/25`이므로 앞 단계는
목표를 함의하지 않는다.

## 4. 존재 증인을 정규화된 값처럼 사용한 경우

### `amc12a_2020_p25`

스케치는 제곱근의 유리수 표현을 임의의 자연수 `u,v`로 얻는다.

```lean
have h_sqrt_rep : ∃ (u v : ℕ),
    (v : ℚ) / u = Real.sqrt (1 - 4 * a) ∧ u ≠ 0 := by sorry
obtain ⟨u, v, hv_sqrt, hu_ne⟩ := h_sqrt_rep
have h_den_sq : a.den = u ^ 2 := by sorry
have h_u : u = 30 := by sorry
```

유리수 표현은 유일하지 않다. 예를 들어 `28/30`과 `56/60`은 같은 값이다. 서로소 조건이나
기약분수 조건 없이 임의로 얻은 `u,v`에 대해 `a.den = u²` 또는 `u = 30`을 결론낼 수
없다. 실제 후보 `a = 29/900`과 Pell 계산 방향은 맞지만, 존재 증인의 선택과 최종 분모를
잇는 의미론적 조건이 빠졌다.

## 5. 필요한 범위보다 강한 거짓 보조정리를 만든 경우

### `imo_1982_p1`

스케치는 다음 전역 폐쇄형을 요구했다.

```lean
have h_form : ∀ n, f n = n / 3 := by sorry
```

원 가정의 함수방정식은 양의 `m,n`에만 적용되므로 `f 0`을 전혀 제한하지 않는다.
따라서 목표 `f 1982 = 660`을 증명할 수 있더라도 `∀ n` 버전은 `n=0` 때문에 일반적으로
성립하지 않는다. 필요한 형태는 적어도 `∀ n, 0 < n → ...`처럼 범위를 제한해야 한다.

## 6. 스케치 유도에 반영할 수 있는 신호

이번 1차 사례에서 생성 직후 검사할 수 있는 신호는 다음과 같다.

1. 원 정리의 작은 경계값을 대입한다. `n=0,1` 반례는 스케치 평가 이전에 잡을 수 있다.
2. `toNat`, `succ`, coercion을 포함한 항은 자연어에서 의도한 변수와 실제 Lean 항의 값을
   작은 예로 대조한다.
3. 점별 부등식은 변수들을 `0`, `1`, 같은 값으로 놓아 sanity check한다.
4. `∃ u v`에서 꺼낸 증인으로 분모·기약성·유일성을 결론내면, coprime 또는 reduced 조건이
   있는지 확인한다.
5. 목표보다 강한 `∀` 보조정리는 원 가정이 그 전체 범위를 실제로 제한하는지 확인한다.
6. 마지막 `have`가 원 목표와 같은 명제이면 의미론적 진전이 없는 재진술로 표시한다.

이 신호들은 have 개수 같은 표면 통계보다 직접적으로 스케치의 수학적 타당성을 측정한다.
다음 분석에서는 명백한 거짓 명제가 없는 시간초과 스케치를 대상으로, 올바른 방향이지만
핵심 난제를 통째로 넘긴 경우와 분해는 적절했으나 prover가 닫지 못한 경우를 분리할 수 있다.

### 7.3 핵심 추가 사례: 스케치에서 독립 서브골로 옮길 때 계약이 달라진다

`mathd_numbertheory_451`의 부모 스케치는 구간·소수·서로 다름 조건을 가지고 있다.
그런데 실제 추출 서명([로그 698367행](../../logs/screen57_20260907_021530.log:698367))은 다음과 같다.

```lean
theorem h_m_structure_h_subset_mathd_numbertheory_451 (n m : ℕ)
    (hm_card : (Nat.divisors m).card = 4)
    (hm_sum : (∑ p in Nat.divisors m, p) = n) :
    ∃ p q, Nat.Prime p ∧ Nat.Prime q ∧ p ≠ q ∧ m = p*q := by sorry

theorem h_sum_eq_h_subset_mathd_numbertheory_451 (m p q : ℕ)
    (hm_eq : m = p*q) :
    (∑ r in Nat.divisors m, r) = (p+1)*(q+1) := by sorry

theorem h_n_eq_2016_h_subset_mathd_numbertheory_451 (n p q : ℕ)

    (h_n_eq : n = (p+1)*(q+1)) : n = 2016 := by sorry
```

- 첫 번째는 `m=8,n=15`가 반례다. 약수가 4개인 수에는 소수의 세제곱도 있다.
  **부모의 구간 가정을 제거한 추출 명제**에 대한 반례이며, 이 값이 원 문제의 구간에

이 문제의 조립 검증은 3/3 유효, prover 검증은 13/29 유효이지만 최종 시간초과다.
**타당한 맥락에서 생긴 스케치라도 추출 후 prover가 받는 명제가 거짓일 수 있다.**
따라서 평가 대상은 자연어/Lean 스케치뿐 아니라
`부모 가정 → 추출된 가정 → 결론`의 보존 관계여야 한다.

### 7.4 목표보다 과도하게 강한 중간 명제가 만든 실패

**AIME 1984 P7**: 원 재귀식으로 계산하면
`f1000=997, f1004=1001, f1001=998, f999=998`이고,
`f1002=999 → f997=998 → f995=998`이다.
따라서 `∀k≤995,f k=997`과 `996≤k≤999 → f k=997`은 둘 다 성립하지 않는다.
목표 `f84=997`을 위해 모든 작은 값을 같은 상수로 만들 필요가 없다.
재귀도 같은 상수 불변식을 유지하므로, prover 추가 호출에 앞서 불변식 수정이 필요하다.

**곱 부등식**: `induction_prod1p1onk3le3m1onn`의 재귀 스케치는

```lean
(3 - 1/(n:ℝ)) * (1 + 1/(n+1)^3) ≤ 3 - 1/(n+1)
```

를 n=0도 포함해 요구한다. 그때 6≤2로 거짓이다.
후반 `h_comb`에는 `0<n'`을 추가하지만, 원 호출이 그 가정을 제공하는지 확인해야 한다.
단순 명제 수정뿐 아니라 n=1 기저 사례와 양의 n 귀납 단계의 연결을 고쳐야 한다.
이 문제는 스냅샷15개, reasoner620회, 서브골 오류 수정 검증0/166이었다.

**IMO 1969 P2**: 분할합에서 곱/나눗셈 오류를 고친 다음에도
`sin((m-n)/2)=0`이라는 과도한 목표를 유지했다.
`k=2, a_i=0, m=π/2,n=3π/2`면 원 함수는 `(3/2)cos x`이고
두 영점의 차는 -π다. 반각 sine은 -1로 0이 아니다.
이는 나눗셈 부호를 고치는 것만으로 해결되지 않는다.
첫 스케치의 진폭 양수 조건은 첫 항의 크기1이 나머지 유한 기하급수 합보다 크다는
구조를 통해 증명하는 후보이나, 현재 성공 검증된 대체 스케치는 아니다.

### 7.5 참인 계산을 반복 분해하는 사례와 표기 문제

`mathd_algebra_158`은 14개 스냅샷 중 최상위1개이고,
나머지 대부분은 합의 Nat→Int 변환과 그 변형이다.
`h_cast_sum`을 다시 같은 결론의 `have`로 넘기거나,
`range8=range8` 같은 자명한 사실을 추가하는 스케치가 있다.
서브골 오류 수정 검증3/256, reasoner801회다.

하지만 **원 표기부터 해석해야 한다**. 로컬 Lean 4.16에서
`open BigOperators Real Nat Topology Rat`를 적용하고
`set_option pp.notation false`로 확인한 결과:

```lean
-- 원문처럼 본문의 덧셈에 괄호가 없으면
(∏ k in Finset.range 6, 2*k+1)
-- 실제 전개:
(Finset.prod (Finset.range 6) (fun k => 2*k)) + 1

(∑ k in Finset.range 5, a+2*k)
-- 실제 전개:
(Finset.sum (Finset.range 5) (fun k => a)) + 2*k
```

첫 곱은 0을 포함하므로 결과가1이고,
`Finset.prod (Finset.range 6) (fun k => 2*k+1)`은 10,395다.
mathlib의 [big operator 우선순위 설명](../../kimina-lean-server/mathlib4/Mathlib/Algebra/BigOperators/Group/Finset/Defs.lean:71)도
덧셈을 본문에 포함하려면 괄호가 필요하다고 명시한다.
서버 설정 파일의 Lean 버전도 v4.16.0이나, 실행 중 서버 REPL의 실제 elaborated AST를
직접 조회한 것은 아니므로 서버 요청 단위 확인은 남아 있다.

명시적인 `Finset.sum/prod`로 의도된 문제를 적으면,
홀수6개 곱의 나머지는 `decide`,
두 유한합에서 a=8을 구하는 것은 `norm_num [Finset.sum_range_succ]`와 `omega`로
로컬 Lean 검증에 성공했다. **원 문자열 그대로를 증명했다는 뜻은 아니다.**
이 차이를 숨기고 “쉬운 문제인데 prover가 못 풀었다”고 하면 연구 라벨이 오염된다.

### 7.6 원 입력 반례가 추가로 확인된 문제

### 8.3 `amc12a_2020_p4`: 올바른 세기 전략에서 정의역이 사라진다

네 자리 수, 모든 자릿수가 짝수, 5의 배수라는 조건으로부터 일의 자리는 0이다.
천의 자리에는 4개, 백·십의 자리에는 각각 5개 선택지가 있어 `4*5*5=100`이라는 전략은 맞다.
첫 스케치는 이 구조를 쓰고 두 번째는 유한 곱집합과 수 인코딩 함수로 구체화한다.

그런데 `hf_inj`는 제한된 자릿수 튜플에서의 단사성 대신 `Function.Injective f`를 요구한다.
재귀 스케치에서 타입을 정리한 형태도 다음 전역 단사성을 그대로 요구한다.

```lean
Function.Injective
  (fun t : (ℕ × ℕ) × ℕ => 1000*t.1.1 + 100*t.1.2 + 10*t.2)
```

이는 `((1,0),0)`과 `((0,10),0)`이 둘 다 1000으로 가므로 거짓이다.
이 반례가 원 문제의 허용된 자릿수 조합일 필요는 없다. 거짓인 것은 **정의역 제한 없이 강화한 서브골**이다.
`Set.InjOn`으로 유한 곱집합에 제한하거나, 자릿수 조건을 가진 subtype으로 정의해야 한다.
튜플도 `(ℕ×ℕ)×ℕ`과 `ℕ×ℕ×ℕ`을 혼용해서 투영 타입이 어긋나는 기록이 있다.

별도 재귀 스케치의 `Nat.digits 10 n = [d3,d2,d1,0]`도 방향이 반대다.
Lean의 `Nat.digits`는 낮은 자리부터 나열하므로 2000의 결과는 `[0,0,0,2]`다.
후속 스케치는 `.head? = some 0`으로 바뀌어 이 부분에는 수정이 관측되지만 전역 단사성은 해결되지 않았다.
따라서 “수정이 있었다”보다 **거짓 계약이 제거되었는지**가 유용한 신호다.

검증 기록은 스케치 2/5, 추출 문법 42/44, subgoal 수정 0/24다.
단사성 반례가 있는 동안에는 증명 예산 증액보다 정의역 복구가 먼저다.
이 사례는 7.3절 mathd451의 추출 가정 누락과 함께, 부모의 유한 범위가 자식 명제에 보존되는지를
자동 비교하는 정책의 표본으로 적합하다.

### 8.4 `amc12b_2021_p13`: 거짓 보조정리를 삭제해도 거짓 후보는 남는다

목표는 `(0,2π]`에서 `1-3*sin x+5*cos(3*x)=0`의 해가 6개임을 보이는 것이다.
네 최상위 스케치는 모두 다음 집합을 답으로 둔다.

`T = {π/3, 2π/3, 4π/3, 5π/3, 7π/6, 11π/6}`.

그러나 `x=π/3`을 대입하면 `cos(3*x)=-1`, `sin x>0`이므로
좌변은 `-4-3*sin(π/3)<0`이다. 따라서 후보 하나만으로도 `T ⊆ S`가 거짓임을 알 수 있다.
첫 스케치의 `cos x = ±1/2 또는 0` 주장도 근거가 없으며, 후속 스케치는 이 주장을 지우면서
같은 T를 유지하고 `h_solution`, `h_T_mem` 등으로 포장한다.

스케치 검증 4/4, 추출 문법 23/23, 조립 검증 4/4가 통과해도 최종 증명은 실패했다.
이 수치는 sorry를 허용한 구조/문법 검증이 거짓 서브골을 판별하지 못함을 특히 선명하게 보여 준다.
관측할 신호는 수정 횟수나 조립 성공 여부보다 **후보 집합의 실제 대입 잔차와 버전 간 후보 동일성**이다.
잘못된 후보를 기각한 뒤 삼각식의 대수화 또는 구간별 근 개수 논증을 다시 설계해야 한다.
현재 로그만으로 그 대안의 증명 비용을 비교한 것은 아니다.

### 8.5 `mathd_algebra_342`: 단순 계산의 반복과 원 표기의 의미

의도한 문제는 5항 합 70, 10항 합 210에서 초항을 구하는 것이다.
최상위 스케치는 `5*a+10*d=70`, `10*a+45*d=210`을 얻어
`d=14/5`, `a=42/5`를 도출한다. **의도된 합을 기준으로는 올바른 구조**다.
15개 재귀 기록은 합의 분배, 상수 합, 곱의 합, cast와 동일한 `h_rewrite`를 반복한다.

하지만 원 입력은 `(∑ k in Finset.range 5, a + k*d)` 형태다.
현재 로컬 Mathlib/Lean 4.16.0에서 이 표기를 외부 `k`와 함께 출력하면 다음처럼 해석된다.

```lean
fun a d k => HAdd.hAdd ((Finset.range 5).sum fun k => a) (HMul.hMul k d)
```

즉 `a+k*d` 전체가 합의 본문이 되지 않는다. 일부 재귀 스케치는 `(a+k*d)`를 괄호로 묶어
의도된 합을 쓰지만, 부모 가정은 기존 표기 그대로다. 따라서 단순히 “prover가 등차수열 계산을
못 했다”고 결론 내리기 전에 부모와 자식의 elaborated 명제가 같은지 확인해야 한다.
실행 당시 서버의 실제 elaborated 요청 전체를 복원한 것은 아니므로, 이 로컬 재현을
곧바로 런타임 실패 원인의 확정으로 해석하지 않는다.

명시적인 `Finset.sum (Finset.range n) (fun k : ℕ => a+k*d)`로 쓴 의도된 두 가정에서는
`norm_num [Finset.sum_range_succ] at h0 h1; linarith`로 목표를 검증했다.
이 검증은 **의도된 명제**에 대한 것이며 원 로그 표기 그대로의 증명 성공을 뜻하지 않는다.
먼저 계약/표기를 확인하고, 의미가 맞아진 이후에는 동일 구조를 유지하는 것이 우선 후보 행동이다.

이 한 문제는 prover 호출 80개, reasoner 호출 755개, subgoal 수정 검증 16/237을 기록했다.
16개 성공은 최종 부모 목표 16개를 닫았다는 뜻이 아니다. 추가 6개의 reasoner 호출 1,024개 중
755개(73.7%)가 여기에 집중되어 있다. 반복 분해 감지와 표기 검사를 먼저 평가할 후보지만,
호출 수는 토큰·실제 GPU 시간과 동일한 비용 척도가 아니다.

### 8.6 나머지 세 문제: 유지할 구조와 명시할 연결

**`amc12a_2003_p23`** — `∏ i∈[1,9],i!`의 소인수 지수는 2,3,5,7에 대해
각각 30,13,5,3이다. `k²`가 이를 나누려면 k의 지수 상한은 15,6,2,1이고,
선택 수는 `16*7*3*2=672`다. 첫 스케치는 제곱 약수 개수로 바꾸고,
두 번째는 지수 튜플의 표현 가능성과 역방향 포함을 적는다.
전략 자체의 반례는 확인되지 않았다. 첫 기록의 `Finset.divisors`, `Nat.IsSquare` 등 API/타입을
확인하고, 두 번째의 `h_bounds`와 `h_surj`에서 카디널리티로 넘어갈 때
**소인수분해 유일성에 따른 튜플 인코딩 단사성**을 명시해야 한다.
양방향 표현 가능성만으로 중복 없는 개수가 자동 확보되지는 않는다.
스케치 검증 1/2, 추출 문법 9/11, 정리 문장 수정 1/12라는 관측도 있어 E를 우선 배정했다.
이것은 구체적 오류 메시지 전부를 API 오류 하나로 귀속한 판정은 아니다.

**`amc12a_2021_p22`** — 세 근 `cos(2π/7), cos(4π/7), cos(6π/7)`에
`8*x³+4*x²-4*x-1=0`을 보이고, 주어진 monic 삼차식을
`x³+(1/2)*x²-(1/2)*x-1/8`과 동일시한 뒤 계수 곱 `1/32`를 얻는다.
핵심 의무는 삼각함수 항등식과 `hpoly_eq`다. 특히 후자는 세 근의 서로 다름과
차수 제한을 사용하는 유일성 증명이 필요하다. 스케치에는 이 연결이 충분히 분리되어 있지 않다.
구조를 유지하되 각도 범위→근의 서로 다름→다항식 차이의 근 개수 같은 국소 연결을 노출하는 것이
우선이다. 스케치 1/1, 추출 문법 6/6, formal 검증 5/14는 전략 완성을 보장하지 않는다.

**`amc12b_2002_p4`** — `1/2+1/3+1/7=41/42`이므로 전체 합은
`(41*n+42)/(42*n)`이다. 정규화된 유리수 분모가 1이라는 가정에서
`42*n ∣ 41*n+42`를 얻고 배수를 1로 제한하여 `n=42`를 도출한다.
이 구조에는 명백한 반례가 없다. 다만 `Rat.den`은 식에 보이는 분모가 아니라 기약분수의 분모이므로,
`n>0`과 정수/자연수 변환을 보존한 나눗셈 보조정리가 필요하다.
스케치의 `hk_one`은 `0<41*n+42<2*(42*n)`(n≥1)와 배수 관계로 분리할 수 있다.
스케치 2/2, 추출 문법 16/16 통과 이후 남은 의무에 대해 이 국소 연결을 확인하는 것이 우선이다.

4. **반례 없이 연결 의무가 구체적인 경우 → 구조 유지와 국소 분해 비교**:

비교하는 후속 실험이 필요하다. 이번 분석은 그 분기 신호와 반례를 정리한 관측 자료다.
