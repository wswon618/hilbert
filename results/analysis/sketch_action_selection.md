## 1. 세 종류의 실패를 어떻게 정의할 것인가

사용자의 세 행동에 대응하여 분석용 실패 유형을 다음처럼 정의한다.

- **국소 계약 결함 → 수정 후보**: 가정·결론·타입·인덱스·부호의 국소 오류.
  고친 뒤 원 목표를 유지하고, 후속 단계에 필요한 명제를 계속 제공해야 한다.
- **분해의 진전 부족 → 재분해 후보**: 핵심 목표 재진술, 필요한 중간 명제 부재,
  불필요한 중복 의무, 자명한 명제로의 후퇴, 동일 미해결 목표 재방문.
- **타당한 의무의 증명 미완료 → 추가 시도 후보**: 현재 가정에서 목표가 타당하다는
  근거가 있고, 분해를 유지한 채 증명 시도를 추가할 가치가 있는 상태.

이는 서로 배타적인 문제 라벨이 아니다. 한 실행이 세 상태를 차례로 거칠 수 있다.
분류 단위는 **한 미해결 노드에서 다음 행동을 선택하는 시점**이어야 한다.
정리문 자체의 반례, 파싱 버전 불일치, 서버 예외, 예산 버그는 별도 환경/데이터 라벨이다.

## 3. 성패 비교군

### IMO 2019 P1: 국소 수정과 구조 개선을 분리할 수 있는 사례

8/31 성공 실행은 269.8분, 스냅샷 13개(공백 제거 후 서로 다른 본문 7개).
첫 골격은 합성 항등식 → 배가 공식 → 가법성 → affine 표현 → 해의 분류다.
기존 문서의 “7개 스케치”와 이번 13개는 중복/재검증 포함 여부가 다르다.

9/3 실패 실행은 600분, 15개 스냅샷이다.
첫 분해는 정방향/역방향 두 의무만 만들었다.
이어 정방향 스케치에는 다음 부호 오류가 있었다.

```lean
have h_eq3 : ∀ z, f (2*z) = 2*f z - f 0 := by sorry
have h_g_eq : ∀ z,
  f (2*z) - 2*(2*z) = 2*(f z - 2*z) + f 0 := by sorry
```

두 번째 식의 마지막 항은 `- f 0`이어야 한다.
원 함수방정식의 해 `f z = 2*z+1`을 대입해도 잘못된 부호를 확인할 수 있다.
후속 스냅샷은 실제로 이 부호를 고쳤지만 최종 실행은 실패했다.
즉 **국소 오류 수정 성공과 원 문제 해결 성공은 다른 결과**다.

- 수정 신호: 앞선 명제로부터 ring/linarith 수준의 대수 관계가 불일치한다.
- 재분해 신호: 부호 수정 뒤에도 `h_cases`가 affine 분류 전체를 그대로 떠안는다.
- 추가 시도 신호: 가법성/affine 표현 등 필요한 전제가 확보된 특정 의무에서
  새로운 유효 증명이 생기는지 확인한다.

반례도 있다. 9/2의 89분 성공 실행 역시 첫 골격은 거칠지만, 재귀에서 가법성·선형성을
구체화하며 성공했다. 따라서 “have가 적다”나 “첫 분해가 거칠다”만으로 폐기하면 안 된다.

모두 적분 비교 전략이다. r1/r2는 비엄격 비교 `sum ≤ integral`와 엄격 비교

정리 선언을 사용할 수 있는 상태의 조립 검증과 모든 정리의 실제 증명 완료를 구별해야 한다.
종료는 reasoner 호출 한도 초과이며, 미완료 부모 의무가 어느 것인지 별도로 추적해야 한다.

이는 반복 수정의 낮은 수율을 보여주지만, 수정 호출 전체 비용이나 최종 성공 기여율은 아니다.
**최근 비용당 부모 의무의 폐쇄가 없는 구간**을 찾아 재분해/추가 증명과 비교할 가치가 있다.
성공한 r3도 같은 수정 검증 수율이 낮으므로, 낮은 비율 하나로 조기 중단하면 오탐한다.

### AMC 2020 P25: 수정이 수학적 정보를 없애는 사례

9/4 실행의 37개 스냅샷 중 최상위는 18개다. 한 변형은 `a=29/900`,
다른 변형은 `a=1/928`을 주장한다. 둘 다 분자+분모가 929라는 답의 형식에는 맞지만
이 사실만으로 어떤 값도 정당화되지 않는다.

후속 수정에서 다음 변화가 실제로 기록된다.

```lean
-- 앞 스케치
have h_int_part : ∀ x ∈ S, (⌊x⌋ : ℤ) ∈ ({0,1,20} : Finset ℤ) := by sorry
have h_card_bound : S.card ≤ 3 := by sorry

-- 수정 후
have h_int_part : True := by sorry
have h_card_bound : S.card ≤ S.card := by sorry
```

그 뒤 `a=1/928`이라는 핵심 의무는 남는다.
또 다른 축약본은 `True`와 최종 목표만 남긴다.
**컴파일/증명 용이성을 높이는 수정이 후속 단계에 필요한 정보를 제거했다.**

이 실행은 조립 검증 33/34 유효, 서브골 오류 수정 검증 0/48 유효이며 최종 시간초과다.
여기서 추가 prover 호출보다 먼저 볼 신호는
(1) 원 가정에서 수치 후보를 도출하는 연결 명제 존재 여부,
(2) 수정 전후 명제의 정보 손실,
(3) 목표와 동치인 의무 재등장이다.

이번 screen57의 분모 증인 문제도 같은 관점에서 읽는다.
`v/u = sqrt(1-4a)`만으로 얻은 임의 증인을 분모의 고유한 표현처럼 쓰고 있다.
단순히 coprime 조건을 붙이면 해결된다는 뜻은 아니다.
예를 들어 28/30은 이미 기약분수가 아니므로, 필요한 것은 분모와 연결되는
**정확한 정규화 관계의 재설계**다.

### AIME 1995 P7: 내용 있는 분해와 답의 나열을 구별하는 사례

8/10 실행에는 스냅샷 112개(최상위 3개, 나머지 재귀)가 있다.
첫 스케치는 `s=sin t+cos t`, `p=sin t*cos t`를 도입하고

`s+p=1/4 → s²-2p=1 → 2s²+4s-3=0 → s의 값 → 유리수/제곱근 분리`

를 전개한다. 다음 변형은 근 선택에 필요한 `s ≥ -sqrt 2`를 추가한다.
이는 필요한 연결 전제를 보충하는 국소 수정 후보다.

후속 `m=13`의 재귀 분해는
`m/n=13/4 → 4m=13n → 서로소성 → n∣4 및 4∣n → n=4 → m=13`으로 이어진다.
전체 실패 실행 안에도 이런 타당한 분해 후보가 있다.
따라서 “이 문제는 계속 실패하므로 모두 재분해”라는 정책은 부적절하다.

반면 screen57 첫 스케치는 `k=10`, `m=13`, `n=4`를 직접 요구하고,
다음 최상위 스케치는 `have hsum : k+m+n=27` 하나다.
필요한 삼각함수 대수화와 유리수/무리수 분리를 생략했다.
이 상태에서는 답의 나열을 더 샘플링하기보다 그 연결 구조를 재분해하는 것이 정책 후보다.

8/10과 8/11 실행의 통계에는 `expected string or bytes-like object`가 기록되어 있다.
따라서 두 실패를 순수한 스케치 실패 실험으로 취급하지 않는다.
긴 실행과 반복 스케치는 분석 재료지만, 그 종료 결과로 정책 효과를 비교할 수는 없다.

## 5. 관측 가능한 신호에서 행동으로

| 시점 | 신호 | 우선 검토할 행동 | 잘못 선택하지 않기 위한 조건 |
|---|---|---|---|
| 스케치 생성 직후 | 부호·범위·증인 조건의 구체적 반례 | 국소 수정 | 원 목표 유지, 수정으로 필요한 전제가 보존됨 |
| 수정 직후 | 유용한 명제가 True/반사성으로 바뀜 | 해당 수정 거부 후 재분해 | 정보 제거가 실제 미사용 의무 제거인지도 확인 |
| 분해 직후 | 부모 목표 재진술, 핵심 연결 명제 부재 | 재분해 | 거친 분해도 재귀에서 개선될 수 있음 |
| 몇 번의 시도 후 | 같은 가정+결론 재등장, 새로운 부모 폐쇄 없음 | 재분해 후보 | 이름 변경은 진전으로 세지 않음 |
| 몇 번의 시도 후 | 가정/목표 타당, 필요한 전제 확보, 증명 후보 개선 | 추가 증명 시도 | 전체 호출 성공률을 해당 의무 성공확률로 사용하지 않음 |
| 어느 시점이든 | 파싱 버전·API 예외·원 정리 반례 | 환경/데이터 처리 | 세 행동 정책의 학습 라벨에 섞지 않음 |

핵심 지표는 잎사귀 성공률이 아니라 **남아 있는 의무 집합이 실제로 줄어드는가**다.
의무의 식별자는 이름 대신 정규화한 가정+결론이어야 한다.
가정을 늘려 얻은 쉬운 증명을 원 의무의 해결로 세면 안 된다.
현재 로그의 이름·시간은 보조 식별자이며, 정확한 의존성/분기 연결은 추가 검증이 필요하다.

## 6. 연구 문제와 비용 평가

좁힌 문제:
**미해결 증명 의무와 지금까지의 관측 이력이 주어졌을 때,
수정·재분해·추가 증명 시도 중 어떤 행동이 동일 성공률에서 남은 비용을 줄이는가?**

입력은 결정 시점까지의 데이터만 사용한다.
최종 성공 여부, 이후 생성된 좋은 스케치, 최종 총 호출 수는 입력에 넣지 않는다.
출력은 세 행동과 작은 추가 예산이다. 신호가 불충분하면 “판단 보류”를 허용한다.

평가는 같은 실패 체크포인트를 복제하여 세 행동에 동일 추가 예산을 주는 방식이 적절하다.
미해결 의무 폐쇄와 원 문제 완료를 따로 측정하고,
prover/reasoner 호출·입출력 토큰·경과 시간을 각각 기록한다.
시간은 병렬 실행 부하에 영향을 받으므로 동일 동시성 조건으로 맞춘다.
기존 Hilbert 정책, 항상 추가 시도, 항상 수정, 항상 재분해와 비교한다.
같은 문제의 스케치가 학습/평가 양쪽에 섞이지 않도록 문제 단위로 나눈다.

지금 로그는 실제 선택한 행동의 결과만 보여준다.
선택하지 않은 행동의 비용/성공확률은 없으므로,
“수정 대신 재분해했으면 N% 절감” 같은 반사실 결론은 낼 수 없다.
표의 행동은 **검증할 정책 가설**이며 신규성과 성능 개선은 아직 확인하지 않았다.
