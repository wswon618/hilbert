# HILBERT 재현 — 수정 내역

Apple 의 HILBERT (arXiv 2509.22819) 를 4×A6000 로컬 서버에서 재현하면서 고친 것들.
**되돌린 실험은 제외하고, 지금 유지 중인 것만 적는다.**

구성: reasoner `gpt-oss-120b`, prover `Goedel-Prover-V2-32B`, 검증기 `kimina-lean-server` (Lean v4.26.0).
목표 수치: 논문의 miniF2F test **90.8%**.

---

## 요약

| 분류 | 건수 | 성격 |
|---|---|---|
| 버그 수정 | 5 | 전부 저장소 원본 결함 |
| 기능 추가 | 2 | 시간 제한, Lean 문법 힌트 |
| 설정 변경 | 5 | 서버 주소, 동시성, 예산, 시간 제한 |
| 데이터 수정 | 1 | miniF2F 정리문 64건 문법 마이그레이션 |
| 새 도구 | 5 | 분할·배치·집계·마이그레이션·코퍼스 검사 |

버그 5건 중 **4건이 조용히 실패하는 종류**였다. 재검색은 한 번도 발동하지 않으면서
로그를 남기지 않았고, 예산 누수는 통계에 잡히지 않았고, 파서는 정상 출력을 버리면서
"형식 오류"로 기록했고, None 크래시는 재시도로 넘어갈 상황을 문제 전체 사망으로 바꿨다.
전부 결과를 나쁘게 만들면서 원인을 감췄다.

# 1. 버그 수정

## 1.1 취소된 호출이 예산을 태움

**파일** `src/tracking/resource_tracking.py`
**대상** `TrackedAsyncLLMClient.simple_chat`, `TrackedAsyncProverLLM.generate_proof`

### 증상

`imo_2019_p1` 이 14시간을 쓰고 `Exceeded maximum number of LLM calls: 700` 으로 죽었다.
그런데 통계 파일에 기록된 호출은 prover 363건, reasoner 387건으로 **양쪽 다 한도 미만**이었다.

### 원인

```python
# 고치기 전
try:
    await self._increment_call_count()          # 카운터 +1  ← 호출 "시작" 시점
    proof = await self.prover_llm.generate_proof(theorem, **kwargs)
    self.stats.add_llm_call(...)                # 통계 +1
except Exception as e:                          # ← CancelledError 가 안 걸림
    self.stats.add_llm_call(...)
    await self._increment_call_count()
```

`asyncio.CancelledError` 는 파이썬 3.8부터 `Exception` 이 아니라 `BaseException` 을 상속한다.
따라서 `except Exception` 을 통과한다. 카운터를 호출 시작 시점에 올려두면, 그 호출이
취소될 때 **카운터만 오르고 통계에는 아무것도 남지 않는다.**

```
python 3.10.20
asyncio.CancelledError 의 상위 클래스: BaseException
issubclass(asyncio.CancelledError, Exception): False

재현 → 카운터 1, 통계 0건
```

HILBERT 는 취소를 대량으로 한다. 병렬 시도 4개 중 하나가 성공하면 나머지를 즉시
취소한다 (`🛑 Stopping all other jobs`, 해당 구간에서 261회).

### 규모

```
설정 예산                    700
통계에 기록된 prover 호출     363
실패분 재증가 (+1)             18
                            ────
재현 가능한 카운터            381
실제 카운터 (예외 발생 시점)   701 이상
                            ────
설명되지 않는 차이            약 320건  ← 취소된 호출

→ 설정한 700 중 실제 증명 시도에 쓴 것은 363회 (52%)
```

이 편향은 **어려운 문제일수록 심하다.** 서브골이 많을수록 병렬 시도가 많고, 그만큼
취소가 많아 실효 예산이 줄어든다. 우리가 관심 있는 것이 정확히 그 문제들이다.

### 수정

카운터 증가를 호출 **뒤로** 옮겼다. 새로 만든 규칙이 아니다 — **같은 파일의
`chat_completion` 이 원래 이 형태였다.** 어긋나 있던 둘을 거기 맞췄다.

```python
# 고친 뒤
try:
    proof = await self.prover_llm.generate_proof(theorem, **kwargs)
    self.stats.add_llm_call(...)
    await self._increment_call_count()          # 기록한 뒤에 +1
except Exception as e:
    self.stats.add_llm_call(...)
    await self._increment_call_count()
```

취소되면 `add_llm_call` 에도 `_increment_call_count` 에도 도달하지 않으므로 기록과
예산이 항상 일치한다. 덤으로 실패 시 카운터가 2씩 오르던 이중 증가도 사라졌다.
이제 네 메서드(`simple_chat`, `chat_completion`, `generate_proof`)가 모두 동일하다.

### 검증

```
취소 1회 → 카운터 0, 통계 0건    (고치기 전: 카운터 1, 통계 0건)
정상 1회 → 카운터 1, 통계 1건
```

### 유의

문제당 시간 제한(600분)을 함께 쓰면, 이 수정이 **정지 시점을 바꾸지는 않는다.**
기록 전체에서 6시간 안에 prover 700회에 도달한 사례가 없다. 이것은 성능 개선이
아니라 정확성 수정이다. 남는 값어치는 (a) 자원 사용량 기록의 정확성,
(b) 어려운 문제에 대한 편향 제거, (c) 예산 통제 실험의 전제 조건이다.

## 1.2 파서가 정상 출력을 버림

**파일** `src/tools/string.py`
**대상** `extract_lean_block`

### 증상

로그에 `No Lean 4 code blocks detected` 가 대량으로 찍히고, 매번
`error_correction_missing_tags` 재요청이 나갔다. `imo_2019_p1` 한 문제에서만 124회,
전체 호출 750회의 **17%** 였다.

### 원인

```python
# 고치기 전
def extract_lean_block(response):
    TRIPLE_TICK_PATTERN = re.compile(r"```(?:lean|lean4)\n?(.*?)\n?```", re.DOTALL)
    ...
```

` ```lean ` 또는 ` ```lean4 ` 로 감싼 것만 받는다. 호출처가 `HILBERTWorker` 에 8곳,
전부 핵심 경로다.

같은 파일에 관대한 `extract_code_block()` 이 있는데 **호출처가 0곳이다.** 저장소가
관대한 버전을 만들어 놓고 쓰지 않았다.

### 실측

로그의 파싱 실패 194건을 본문까지 복원해 분류했다.

```
현재 규칙으로도 통과        14건  ( 7.2%)   본문 복원 오차
태그 없는 ``` 블록           0건  ( 0.0%)
울타리 없는 순수 Lean 코드   94건  (48.5%)   ← 복구 가능
그 외 (산문)                86건  (44.3%)   ← 진짜 실패
```

전형적인 손실 사례. 내용에 아무 문제가 없다.

```lean
by
  have h_num_div_den : (a.num : ℚ) / a.den = a := by
    exact h_num_div_den_amc12a_2020_p25 a
  ...
  exact h_goal
```

나머지 44% 는 `"I'm sorry, but the statement as given cannot be proved..."` 같은
산문이다. 형식 문제가 아니라 모델이 포기한 것이라 파서를 완화해도 살릴 수 없다.

### 수정

단계적 후퇴를 넣었다. 1단계(원래 규칙)는 손대지 않았다.

```
1단계  ```lean / ```lean4       저장소 원래 규칙, 그대로 유지
2단계  ``` + 아무 태그           언어 태그를 빠뜨린 경우
3단계  울타리 없는 순수 코드      응답이 Lean 으로 시작할 때만
```

3단계의 시작 토큰 조건이 안전장치다.

```python
_BARE_LEAN_START = re.compile(
    r"^\s*(?:by\b|theorem\b|lemma\b|example\b|have\b|import\b|open\b|set_option\b|·|--)"
)
```

산문은 이 패턴에 걸리지 않아 지금처럼 실패로 남는다. 잘못된 것을 Lean 코드로
오인해 넣을 위험이 없다.

### 검증

같은 로그의 실패 200건에 새 파서를 적용했다.

```
회수됨     109건  (54.5%)
여전 실패   91건  (45.5%)   ← 산문 등 진짜 실패
```

회수된 것을 표본으로 확인하니 전부 정상 Lean 코드였다.

## 1.3 빈 응답이 문제 전체를 죽임

**파일** `src/tools/string.py`, `src/models/HILBERTWorker.py`

### 증상

`imo_2019_p1` 이 32.6분 만에 파이썬 예외로 죽었다. 시간 초과도 예산 소진도 아니다.

```
TypeError: expected string or bytes-like object

  string.py:157           re.findall(lean_pattern, response, ...)
  HILBERTWorker.py:1574   missing_theorems = extract_all_lean_blocks(missing_response)
```

### 원인

`missing_response` 가 `None` 이었다. 이 자리는 reasoner 에게 "스케치에서 빠진 서브골을
다시 뽑아달라"고 묻는 곳이고, `reasoning={'effort': 'high'}` 로 부른다. gpt-oss-120b 가
추론 토큰만 쓰고 본문을 비워 보내면 `chat_completion` 이 `None` 을 반환한다.

`re` 모듈은 C 레벨에서 문자열 버퍼를 직접 훑는다. `None` 은 버퍼가 없어 스캔을
시작할 수조차 없다.

```
re.findall(패턴, "정상 문자열")  →  []           정상
re.findall(패턴, "")            →  []           정상 — 길이 0인 버퍼
re.findall(패턴, None)          →  TypeError    버퍼 자체가 없음
```

### 왜 문제 전체가 죽는가

예외를 잡아줄 핸들러가 중간에 없어서 6단계를 거슬러 올라간다.

```
string.py:157               re.findall(..., None)          ← 발생
HILBERTWorker.py:1574       extract_all_lean_blocks(...)
HILBERTWorker.py:1476       _check_and_extract_missing_subgoals(...)
HILBERTWorker.py:2043       extract_subgoals_from_sketch(...)
HILBERTWorker.py:1002       _correct_proof_sketch_and_extract_theorems(...)
HILBERTWorker.py:1057       _single_subgoal_decomp_attempt(...)
HILBERTWorker.py: 946       subgoal_decomp(...)
AsyncHILBERT.py: 182        asyncio.wait_for(coro, ...)    ← 여기서 처음 잡힘
                            except Exception → 문제 전체를 실패로 반환
```

저자는 방어를 하려 했다. 바로 아래 줄에 이것이 있다.

```python
missing_theorems = extract_all_lean_blocks(missing_response)   # ← 여기서 터짐

if missing_theorems is None:
    continue    # 다음 시도로 넘어감 — 도달하지 못함
```

`None` 이 **반환될** 가능성은 생각했지만 `None` 이 **입력될** 가능성은 생각하지 않았다.
원래 의도는 "실패하면 재시도" 였는데 실제로는 "실패하면 문제 전체 사망" 이 됐다.

### 수정

`string.py` 의 추출 함수를 전수 점검했다. **넷 중 셋이 무방비였다.**

| 함수 | 조치 | 호출 위치 |
|---|---|---|
| `extract_all_lean_blocks` | `None` 반환 | HILBERTWorker.py:1574 (크래시 지점) |
| `extract_search_queries` | `[]` 반환 | HILBERTWorker.py:691 |
| `extract_theorems_queries` | `[]` 반환 | HILBERTWorker.py:722 |
| `extract_tag` | `None` 반환 | HILBERTWorker.py:426, 831, 852 |

추가로 `HILBERTWorker._check_and_extract_missing_subgoals` 에서 빈 응답을 대화 기록에
넣지 않고 다음 시도로 넘어가게 했다. `content=None` 인 메시지를 남기면 이후 호출까지
오염된다.

```python
if not missing_response:
    logger.info("Empty response while extracting missing subgoals; retrying.")
    continue
```

### 왜 이제야 터졌나

`None` 이 나오려면 모델이 본문을 비워 보내야 하는데 드물다. 기준선 실행에서 이 경로를
6번, 다음 실행에서 10번 지났는데 매번 정상 응답이 왔다. `TypeError` 는 "예상된 실패"가
아니라 프로그래밍 오류라서 아무도 핸들러를 쓰지 않는다. 이런 종류는 발현될 때까지
조용히 잠복한다.

## 1.4 오류 기반 재검색이 한 번도 작동하지 않음

**파일** `src/tools/lean_utils.py`

### 원인

```python
# 고치기 전
unknown_constant_pattern   = r"unknown constant\s+'([^']+)'"
unknown_identifier_pattern = r"unknown identifier\s+'([^']+)'"

# 고친 뒤
unknown_constant_pattern   = r"unknown constant\s+['`]([^'`]+)['`]"

```
Unknown constant `Complex.abs`

만났을 때 다시 검색하는 경로 자체가 죽어 있었다.

## 1.5 연결 교착

**파일** `src/tools/AsyncLLMClient.py`

### 증상

11시간 동안 프로세스가 멈춰 있었다. 서버 3개는 전부 정상이었다.

```
ESTABLISHED   0
CLOSE_WAIT   15     ← 서버가 닫았는데 클라이언트가 안 닫은 소켓
프로세스 상태  ep_poll 에서 대기
```

### 수정

```python
import httpx

self.http_client = httpx.AsyncClient(
    limits=httpx.Limits(
        max_connections=64,
        max_keepalive_connections=0,   # 유휴 연결을 남기지 않는다
    ),
)
self.client = openai.AsyncOpenAI(
    base_url=self.base_url,
    default_headers=self.default_headers,
    timeout=httpx.Timeout(
        connect=10.0,                  # 로컬 서버 연결에 40분을 줄 이유가 없다
        read=float(self.timeout),      # 생성 대기는 기존대로 길게
        write=60.0,
        pool=60.0,                     # 풀이 막히면 60초 뒤 예외 → 그 문제만 실패
    ),
    max_retries=3,
    http_client=self.http_client,
)
```

`max_keepalive_connections=0` 이 핵심이다. 유휴 연결을 남기지 않으면 CLOSE_WAIT 가
쌓일 자리가 없어진다. 로컬 vLLM 이라 연결 비용은 무시할 수준이다.

### 검증

```
고치기 전   ESTABLISHED 0 / CLOSE_WAIT 15   11시간 무응답
고친 뒤     ESTABLISHED 4 / CLOSE_WAIT  1   40분 만에 정상 종료
```

**생성 내용에 영향을 주는 설정은 하나도 건드리지 않았다** (프롬프트, 온도,
`max_tokens`, 정지 토큰 모두 그대로).

# 2. 기능 추가

## 2.1 문제당 시간 제한

**파일** `src/models/AsyncHILBERT.py`, `src/tracking/ProofAttemptConfig.py`,
`configs/experiment/async_hilbert.yaml`

### 왜 필요한가

호출 한도만으로는 실행 시간이 묶이지 않는다. 호출 수와 시간의 관계가 들쭉날쭉하다.

```
prover 호출     소요        분/호출
      4       67.8분      16.96
      4      154.5분      38.63    ← 호출 4번에 2시간 반
     20        8.3분       0.41
    300      199.1분       0.66
   3896      747.3분       0.19

분/호출 범위  0.03 ~ 38.63   (1000배 차이)
```

`aime_1999_p11` 은 prover 를 4번 부르고 154분을 썼다. 시간이 prover 가 아니라
reasoner 와 Lean 검증에서 나갔기 때문이다. 그 결과 실패하는 문제가 13~18시간씩
태우는 일이 반복됐다.

### 값의 근거

보관된 기록 109건으로 측정했다.

| 제한 | 유지되는 성공 | 누적 시간 | 절감 |
|---|---|---|---|
| 없음 | 84/84 | 182시간 | – |
| 60분 | 70/84 | 48시간 | 74% |
| 120분 | 77/84 | 67시간 | 63% |
| 180분 | 80/84 | 83시간 | 54% |
| 360분 | 83/84 | – | – |
| **600분** | **84/84** | – | – |

성공한 84건 중 가장 오래 걸린 것이 581분(`algebra_9onxpypzleqsum2onxpy`).
600분이면 기록상 모든 성공 사례를 포함한다.

다만 581분은 그 문제의 고유 난이도가 아니라 운이 나빴던 실행이다. 같은 문제가 다른
실행에서는 333분에 풀렸고, `aime_1987_p5` 도 199분/153분으로 갈렸다. 소요는 난수에
따라 3배까지 벌어진다.

### 구현

```python
timeout_s = getattr(self.proof_attempt_config, "per_problem_timeout_seconds", None)

async with await self._create_worker() as worker:
    coro = worker.generate_single_proof(formal_statement, header, problem_id)
    try:
        if timeout_s:
            success, proof = await asyncio.wait_for(coro, timeout=timeout_s)
        else:
            success, proof = await coro
        return problem_id, success, proof
    except asyncio.TimeoutError:
        logger.error(f"Problem {problem_id} exceeded the per-problem time limit "
                     f"({timeout_s}s); giving up on it and moving on.")
        return problem_id, False, None
```

`wait_for` 가 코루틴을 취소해도 `generate_single_proof` 의 `finally` 블록이 돌아
**통계 파일은 정상 저장된다.** 시간 초과로 끝난 문제도 어디까지 갔는지 분석할 수 있다.

`None` 이면 기존처럼 무제한이라, 이 필드를 넣지 않은 설정에는 영향이 없다.

### 유의

이 값이 실질적인 정지 조건이 된다. 호출 한도(700/1500)는 6시간 안에 도달한 기록이
없어 거의 발동하지 않는 상한선으로 남는다. **결과를 보고할 때 "문제당 600분 제한"을
명시해야 하고, 논문의 호출 예산 조건과 동일하다고 말할 수 없다.**

# 4. 데이터 — miniF2F 문법 마이그레이션

**산출물** `data/minif2f/minif2f_lean4_26.jsonl` (원본은 그대로 둠)
**도구** `scripts/migrate_dataset_syntax.py`

## 문제

miniF2F 는 mathlib 이 `∑ x in s, f x` 표기를 쓰던 시절에 만들어졌다. 이후 mathlib 이
이 표기를 없애면서 Lean v4.26 에서는 파싱조차 되지 않는다.

```
∑ k in S, k   →   unexpected token 'in'; expected ','
```

**정리문 자체가 컴파일되지 않으므로 모델이 무엇을 하든 그 문제는 실패한다.**

## 규모 — 전수 검사

정규식으로 의심 패턴을 세는 대신 **488문제를 전부 Lean 에 넣어 컴파일했다.**
어떤 종류의 파손이든 컴파일러가 잡아낸다.

```
                        test          valid
구버전 문법 포함          31문제         33문제   (12.7% / 13.5%)
치환 후 컴파일 실패        0건            0건
그 외 컴파일 실패          1건            0건     ← Complex.abs
```

전수 검사라서 정규식이 놓쳤을 가능성이 없다. 실제로 정규식이 놓친 것을 두 종류 잡아냈다.

## 왜 치환을 믿을 수 있는가

믿지 않는다. 대신 검증한다.

데이터셋의 각 항목에는 `goal` 필드가 있다. 이것은 데이터셋을 만들던 당시의
(구 표기를 파싱할 수 있던) Lean 이 정리문을 elaborate 한 뒤 출력한 목표 상태다.
그 출력에는 이미 `∈` 이 쓰여 있다 — **Lean 자신이 `in` 을 받아 `∈` 으로 정규화했다는
뜻이고, 따라서 두 표기는 같은 항(term)이다.**

```
구 표기 ──(옛 Lean)──▶ goal_A          [데이터셋에 이미 있는 값]
       ──(치환)──▶ 신 표기 ──(우리 Lean)──▶ goal_B

goal_A == goal_B  이면 서로 다른 두 버전의 Lean 이 같은 항에 도달한 것
```

우리 Lean 은 구 표기를 읽지 못하니 이 값을 스스로 만들 수 없다. 데이터셋에 남아 있는
값을 오라클로 쓴다.

## 판정 기준

goal 을 통째로 비교하면 안 된다. Lean v4.26 의 출력기가 바뀌어서, **우리가 전혀
손대지 않은 문제에서도** goal 이 달라진다 (대조군에서 test 30건 / valid 28건 확인).

```
n !          vs  n.factorial
(π/7).cos    vs  cos (Real.pi/7)
Nat.Prime p  vs  p.Prime
Finset.filter (fun x => p x) s  vs  {x ∈ s | p x}
```

우리가 손대지 않은 문제에서 같은 종류의 차이가 나타난다는 것이, 원인이 우리 편집이
아니라 Lean 버전임을 증명한다. 그래서 다음 둘 중 하나면 받아들인다.

- **(a)** 편집이 `in` → `∈` 표기 치환뿐이다. 데이터셋의 goal 이 두 표기의 동등성을
  이미 증명했으므로, 표기만 바꾸고 컴파일이 되면 의미는 보존된다.
- **(b)** goal 의 큰 연산자 binder 구간이 일치한다. 괄호가 늘어난 경우에 쓴다.

## 두 가지 특수 사례

### 타입 표기 binder (valid 2문제)

새 문법에는 `∑ (k : ℤ) ∈ s,` 형태가 없다. Lean 에 직접 물어 확인했다.

```
∑ (k : ℤ) ∈ Finset.Icc 1 12   →  unexpected token '∈'
∑ k ∈ (Finset.Icc 1 12 : Finset ℤ)   →  통과
```

타입을 binder 가 아니라 집합 쪽으로 옮긴다. 치환 후 goal 이 데이터셋의 원래 goal 과
일치함을 확인했다.

```lean
- ∑ k : ℤ in Finset.Icc 1 12, z ^ k ^ 2
+ ∑ k ∈ (Finset.Icc 1 12 : Finset ℤ), z ^ k ^ 2
```

### `Complex.abs` (test 1문제, 미수정)

`amc12a_2020_p15` 는 표기가 아니라 **삭제된 API** 를 쓴다. mathlib 이 `Complex.abs` 를
없애고 노름 `‖·‖` 로 통일했다.

`‖a - b‖` 로 바꾸면 컴파일되고 `Complex.norm_eq_sqrt_sq_add_sq` 로 두 값이 같음도
증명된다. 그러나 이 연결은 **데이터셋의 goal 이 증명해주지 않는다** — goal 에도
`Complex.abs` 라고 적혀 있다. 앞의 64문제와 같은 등급의 근거가 아니다.

표기 변경이 아니라 수식을 다시 쓰는 것이라, 0.4%p 를 얻자고 데이터셋 수정의 성격을
바꾸지 않기로 했다. **의도적으로 두었다.**

# 5. 조사했으나 바꾸지 않은 것

## 5.1 검색 코퍼스 최신화

`cache/mathlib_informal.jsonl` 은 mathlib v4.16 시점에 만들어졌고 지금 Lean 은 v4.26 이다.
전수 검사 결과 **187,540개 중 9,039개(4.8%)** 가 현재 mathlib 에 없다
(`scripts/check_corpus_names.py`, 목록은 `cache/stale_names.txt`).

그런데 실제 오류의 출처를 세어보니 코퍼스는 주범이 아니었다.

```
로그의 unknown constant/identifier  164종 / 2,685건

  코퍼스에 있음 (검색이 건넨 노후 이름)     6종    189건    7.0%
  코퍼스에 없음 (모델이 기억으로 생성)    158종  2,496건   93.0%
```

**93% 는 검색이 건넨 적 없는, 모델이 학습 기억에서 꺼낸 이름이다.** 코퍼스를 최신으로
바꿔도 7% 만 해결된다. 그래서 코퍼스 교체를 보류했다.

쏠림도 극단적이다.

```
상위 9종 = 1,550건 (58%)   전부 pow_le_pow / pow_lt_pow 계열
```

2024년 mathlib 이 이 계열을 `_left`/`_right` 로 정비한 단일 개편 하나가 원인이다.

## 5.2 이름 변경 지도

mathlib 은 이름을 바꿀 때 `@[deprecated] alias 옛이름 := 새이름` 을 남긴다. 현재 소스에
4,378건 있지만, 우리에게 필요한 옛 이름들은 이미 삭제된 뒤였다.

```
#check @pow_le_pow_left  →  Unknown identifier `pow_le_pow_left`   (deprecated 경고가 아님)
```

로컬 mathlib 이 `--depth 1` 로 받아져 히스토리도 없다. 원격 태그(v4.22~v4.33)는
접근되므로, 과거 태그 몇 개를 얕게 받아 그 시점의 별칭 표를 긁어 합치면 **손으로 쓴
표가 아니라 mathlib 공식 기록에서 파생된 지도**를 만들 수 있다. 아직 하지 않았다.

## 5.3 `NON_COT_PROMPT` 의 따옴표 불일치

`src/prompts/formal_to_formal.py` 에서 `COT_PROMPT` 는 백틱, `NON_COT_PROMPT` 는
작은따옴표를 쓴다. 처음에는 이것이 파싱 실패의 원인이라고 봤으나, 실제 로그를
확인하니 **모델은 프롬프트와 무관하게 항상 백틱으로 답한다.** 원인이 아니었다.

# 8. 재현성에 대한 관찰

`imo_2019_p1` 은 같은 코드·같은 설정에서 한 번은 270분에 성공하고 한 번은 840분 쓰고
실패했다. 상세 비교는 `results/analysis/imo_2019_p1_비교.md` 에 있다.

```
prover   temperature = 0.6   (src/inference/AsyncProverLLM.py:51)
reasoner temperature = 0.6   (AsyncLLMClient 기본값)
seed     설정 없음
```

prover 의 한 방 성공률은 두 실행에서 36% 대 37% 로 같았다. 갈린 것은 reasoner 가 만든
분해의 질이다. 성공한 실행은 첫 스케치(`have` 8개)가 그대로 최종 증명의 골격이 됐고,
실패한 실행은 첫 스케치가 `have` 18개로 잘게 쪼개진 뒤 38가지 변형을 14시간 동안
배회했다.

**같은 문제가 다른 실행에서 3배까지 다른 시간을 쓴다.** 한 번의 실행으로 "풀린다 /
안 풀린다" 를 말할 수 없다. 15문제 규모의 대조 실험에서는 이런 문제 하나가 결과를
흔들 수 있으므로, 결론을 낼 때 반복 실행이 필요하다.
