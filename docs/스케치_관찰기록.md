# HILBERT 스케치 생성 — 관찰 기록

Apple HILBERT (arXiv 2509.22819) 를 4×A6000 로컬 재현하면서 수집한, **증명 스케치**
(Algorithm 2 의 서브골 분해) 동작에 대한 관찰이다. 독립 연구를 위한 원자료 정리이며,
여기서 제시하는 것은 **측정된 사실과 코드에서 확인한 구조**다. 개선안은 마지막에 따로 둔다.

```
환경   reasoner  gpt-oss-120b        (vLLM, temperature 0.6)
       prover    Goedel-Prover-V2-32B (vLLM, temperature 0.6)
       검증기    kimina-lean-server   (Lean v4.16.0 / v4.26.0)
       seed      설정 없음
자료   4회 실행, 270개 스케치, 86개 (실행×정리) 조합
```

---

# 1. 스케치란 무엇인가 (코드 기준)

HILBERT 는 문제를 직접 못 풀면 **스케치**를 만들어 서브골로 나눈다.
스케치는 `have` 로 보조정리를 나열하고 각 본문을 `sorry` 로 둔 Lean 코드다.

```lean
theorem imo_2019_p1 (f : ℤ → ℤ) : ... := by
  constructor
  · intro h
    have h_c_eq   : ∀ b, f (f b) = f 0 + 2 * f b := by sorry
    have h_f2a_eq : ∀ a, f (2 * a) = 2 * f a - f 0 := by sorry
    have h_add_eq : ∀ a b, f (a + b) = f a + f b - f 0 := by sorry
    ...
```

생성 절차는 `HILBERTWorker.generate_proof_sketch` (398행) 에서 두 단계다.

```
1. INFORMAL_LLM_INFORMAL_PROOF_SKETCH   자연어 증명 개요를 쓰게 한다
2. INFORMAL_LLM_CREATE_LEAN_SKETCH      그 개요를 Lean have 나열로 옮긴다
```

만들어진 스케치는 `sorry` 를 넣은 채 Lean 으로 검증한다(`proof_sketch_with_sorry_verification`).
컴파일되면 `have` 들을 독립 정리로 추출해(`subgoal_extraction`) 각각을 증명하고,
전부 닫히면 원 스케치에 끼워 넣어 다시 검증한다(`sketch_assembly`).

네 번의 유효한 실행에서 두 번 풀렸는데, **풀린 두 번 모두 스케치 1개**였고
실패한 두 번은 3개와 37개였다. 문제 난이도는 같다.

# 3. 재시도가 학습하지 않는다

## 3.1 프롬프트에 과거 시도가 들어가지 않는다

`generate_proof_sketch` (398~450행) 가 만드는 프롬프트의 인자는 둘뿐이다.

```python
input_prompt = INFORMAL_LLM_INFORMAL_PROOF_SKETCH.format(
    problem=problem,
    useful_theorems_section=useful_theorems_section
)
```

`problem` 은 정리문, `useful_theorems_section` 은 검색된 관련 정리다.
**직전 스케치가 무엇이었는지, 왜 실패했는지는 전달되지 않는다.**

## 3.2 재시도 루프도 인자가 같다

`subgoal_decomp` (1027행) 의 재시도 구성이다.

```python
args_for_each_job = [(problem, header, depth, i+1)
                     for i in range(2 * self.proof_config.subgoal_decomp_attempts)]
for args_tuple in args_for_each_job:
    result, valid = await self._single_subgoal_decomp_attempt(*args_tuple)
```

8번의 시도가 **완전히 동일한 인자**로 호출된다. 차이는 `i+1`(시도 번호)뿐이고
그것은 로그 출력에만 쓰인다. 서로 다른 결과를 기대하는 근거는 온도 0.6 의 무작위성뿐이다.

## 3.3 그 결과 — 같은 스케치의 재방문

`algebra_sum1onsqrt2to1onsqrt10000lt198` (R4, v4.16) 에서 만든 32개 스케치의
`have` 이름 조합을 보면 반복이 드러난다.

```
h_cont_sqrt, h_pos, h_sqrt_ne_zero, h_cont_inv, h_eq      ← 10, 15, 19, 27, 32번 (5회)
h_integrable, h_add_adjacent, h_base, h_induction, h_result ← 6, 9, 26번 (3회)
h_int, h_sum_eq, h_reindex                                 ← 7, 8, 14번 (3회)
hab_int, hbc_int, h_add                                    ← 16, 29번 (2회)
h_fun, h_int, h_ae_disjoint, ...                           ← 24, 28번 (2회)
```

32개 중 실질적으로 다른 접근은 10개 남짓이다. 나머지는 이미 실패한 곳으로 되돌아간 것이다.

전체 자료에서 재방문 비율은 이렇다.

| 수준     | 조합 수 | 스케치 | 같은 have 조합 재방문 | 비율  |
|--------|------|-----|----------------|-----|
| 최상위 정리 | 19   | 73  | 15             | 21% |
| 재귀 서브골 | 67   | 197 | 49             | 25% |

**재귀 깊은 곳일수록 재방문이 많다** (25% 대 21%). 깊이 들어갈수록 문맥이 좁아져
모델이 같은 결론에 반복해서 도달하는 것으로 보인다.

# 4. 스케치 크기의 궤적

`have` 개수를 시간순으로 늘어놓으면 두 가지 양상이 나타난다.

## 4.1 수렴 — 성공 사례

```
imo_2019_p1 (R1, 성공)      8 → 7 → 6 → 7 → 7 → 6 → 4
```

1번이 최상위 골격이고 2~7번은 그 안의 어려운 서브골(`h_cases`)을 재귀 분해한 것이다.
**남은 문제가 실제로 작아지고 있다.**

## 4.2 축소 — 실패 사례 (`amc12a_2020_p25`, R4)

```
 1. have 10개  43줄   ha_eq, h_def, h_quad, h_ineq, h_m
 5. have 10개  35줄
 8. have  8개  24줄
10. have  9개  17줄   h_mem_eq, h_decompose, h_quad_eq  ← 접근법 교체
13. have  6개  16줄
15. have  5개  14줄
17. have  6개  17줄
```

43줄에서 14줄까지 줄었다. 같은 문제를 **점점 성기게** 나누고 있다.
4.1 과 겉보기는 비슷하지만 성격이 다르다 — 남은 문제가 작아진 것이 아니라
같은 문제를 더 굵은 덩이로 뭉갠 것이다.

`complexity_proof_length_cutoff: 30` 이 관여했을 가능성이 있다. 30줄이 넘는 증명
시도는 잘려나가므로(로그의 `Ending proof attempt early because of complexity`,
이 실행에서 27회), 모델이 짧은 쪽으로 밀릴 유인이 있다. **다만 이 인과는 확인되지 않았다** —
프롬프트에 그 피드백이 전달되지 않으므로(3.1), 직접적 경로는 없다.

## 4.3 진동 — 실패 사례 (`imo_2019_p1`, R2)

```

→ 10 → 5 → 3 → 5 → 5 → 4 → 4 → 4 → 3 → 3 → 4 → 4 → 4 → 3 → 3 → 3 → 3 → 3 → 5 → 4
```

38개 스케치가 3~6 사이를 34번 오간다. 14시간 동안 수렴하지 않았다.

# 5. 재귀 스케치

서브골이 안 닫히면 그 서브골을 다시 분해한다(`_verify_and_correct_subgoal`, 1278행).
이때 만들어지는 스케치가 전체의 대부분이다.

| 수준             | 스케치 수 | 비율  |
|----------------|-------|-----|
| 최상위 정리에 대한 스케치 | 73    | 27% |
| 재귀 서브골에 대한 스케치 | 197   | 73% |

서브골 이름이 부모 이름을 이어붙여 만들어지므로, 이름 길이가 재귀 깊이를 드러낸다.

```
깊이 4  h_sum_lt_h_sum_lt_integral_h_sum_lt_h_goal_h3_algebra_sum1onsqrt2to1onsqrt
깊이 3  h_sum_lt_integral_h_sum_lt_h_goal_h3_algebra_sum1onsqrt2to1onsqrt10000lt19
깊이 3  h_sum_eq_h_result_h_integral_eq_sum_h_lt_int_algebra_sum1onsqrt2to1onsqrt1
깊이 3  h_right_h_sum_eq_h_sum_le_integral_hsum_le_algebra_sum1onsqrt2to1onsqrt100
깊이 3  h_pointwise_h_sum_lt_h_goal_h3_algebra_sum1onsqrt2to1onsqrt10000lt198
깊이 3  h_int_h_result_h_integral_eq_sum_h_lt_int_algebra_sum1onsqrt2to1onsqrt1000
```

## 5.1 통계의 `max_depth_reached` 는 신뢰할 수 없다

모든 실행의 통계에 `max_depth_reached: 0` 이 기록되지만, 실제로는 재귀가 일어난다.
`StrategyTracker` 를 만드는 다섯 자리 모두 `depth` 를 리터럴 `0` 으로 넘기기 때문이다.

```python
StrategyTracker(self.stats, StrategyType.SKETCH_GENERATION, 0, ...)   #  403행
StrategyTracker(self.stats, StrategyType.FORMAL_LLM,        0, ...)   #  931행
StrategyTracker(self.stats, StrategyType.SUBGOAL_DECOMP,    0, ...)   #  945행
StrategyTracker(self.stats, StrategyType.SHALLOW_SOLVE,     0, ...)   # 1092행  ← depth 인자를 받고도 0
StrategyTracker(self.stats, StrategyType.SKETCH_ASSEMBLY,   0, ...)   # 1812행
```

```python
# ProofStatistics.py:312
self.max_depth_reached = max((a.depth for a in self.strategy_attempts), default=0)
```

실제 깊이는 로그로 확인해야 한다.

```
                                        R3(v4.26)  R4(v4.16)
PARALLEL ATTEMPTS FAILED, TRYING RECURSIVE   17회      21회
Recursive proof succeeded                     7회       5회
MAX DEPTH REACHED, CANNOT RECURSE FURTHER     0회       2회
```

**재귀 스케치 연구를 하려면 이 지표를 먼저 고쳐야 한다.**

# 6. 사례 연구

## 6.1 aime_1999_p11 — 첫 스케치로 끝난 경우

```
스케치 생성 1회   조립 1회   소요 62.6분   호출 44 (prover 24, reasoner 20)
sorry 검증 100%   조립 검증 100%   정리문 추출 100%
```

reasoner 가 만든 분해가 AIME 정답 풀이 그대로였다.

```
hsum_eq    ∑ sin(5k°) = tan(175/2°)      핵심 — 곱→차 변환 후 텔레스코핑
htan_eq    tan(m°) = tan(175/2°)
h_range    0 < m° < π/2                   tan 단사성의 전제
h_inj      m° = 175/2°                    Real.tan_inj_of_lt_of_lt_pi_div_two
hm_eq      (m : ℝ) = 175/2
hm_rat     m = 175/2  (ℚ 로)
num_eq     m.num = 175
den_eq     m.den = 2
final_eq   den + num = 177
```

같은 문제를 v4.26 에서 돌린 R3 에서는 스케치 2개, 서브골 30개 중 29개를 닫고
`h_sum_cot`(같은 핵심 보조정리) 하나에서 막혀 600분 제한에 걸렸다.
**분해는 두 번 다 옳았다.** 갈린 것은 그 조각을 닫을 수 있었는지다.

## 6.2 amc12a_2020_p25 — 분해는 안정적, 조각이 안 닫힘

```
스케치 생성 2회   조립 18회   서브골 22개 중 6개 미해결
prover 254회 호출, 유효율 36%
못 닫은 서브골: h_m, h_a, h_result, h_s_val, h_vals, h_sum_calc  (전부 최상위)
```

스케치를 2번만 만들었다는 것은 분해가 안정적이었다는 뜻이다. 그런데 조립을 18번 시도했다.
서브골이 구체적 계산(해의 목록, 그 합)을 요구했고 prover 가 못 닫았다.

## 6.3 algebra_sum1onsqrt — 분해 발산

```
스케치 생성 25회   조립 28회   shallow_solve 108회
서브골 92개 중 10개 미해결
reasoner 1,502회로 한도(1500) 소진 → 300분에 종료
sorry 검증 57%  ← 만든 스케치의 절반이 컴파일도 안 됨
형식 재요청 389회 (전체 호출의 21%)
```

`∑ 1/√k < 198` 을 적분 비교로 증명하려면 측도론적 준비(가측성, 적분가능성, 구간 분할)가
필요한데, 그 준비가 계속 새 서브골을 낳았다. 서브골 이름이 4~5단계까지 길어진다.

# 7. 연구 거리

관찰에서 자연스럽게 나오는 질문들이다. 어느 것도 아직 검증하지 않았다.

## 7.1 첫 스케치 품질의 예측 가능성

```
성공 8건 중 7건이 스케치 1개로 끝났다.
→ 첫 스케치를 여러 개 뽑아 고르는 것이 이득인가?
→ 어떤 기준으로 고를 것인가? (have 개수? sorry 검증 통과? 서브골 난이도 추정?)
```

현재 구현은 스케치를 하나 만들어 실패하면 버리고 새로 만든다.
동시에 N 개를 만들어 비교하는 구조는 없다.

## 7.2 재시도에 실패 정보를 넣으면

```
현재  프롬프트 = (문제, 검색된 정리)
대안  프롬프트 = (문제, 검색된 정리, 실패한 스케치 목록, 각각의 실패 사유)
```

재방문 비율(최상위 21%, 재귀 25%)이 줄어드는지, 줄어들면 성공률이 오르는지.

주의: 이것은 논문 Algorithm 2 를 벗어나는 변경이다. 재현 실험과 분리해야 한다.

## 7.3 스케치 크기의 최적 구간

```
관측된 실패:  첫 have 18개 (너무 잘음), 첫 have 2개 (너무 굵음)
관측된 성공:  첫 have 3, 8, 9, 10, 11, 15, 16개
```

표본 19건으로는 결론을 못 낸다. 같은 문제를 반복 실행해 첫 스케치 크기와 성공률의
관계를 재는 실험이 필요하다. 온도를 바꿔 크기 분포를 움직일 수 있는지도 볼 만하다.

## 7.4 `complexity_proof_length_cutoff` 의 효과

```
현재 30줄. 넘으면 그 시도를 버리고 재귀 분해로 넘어간다.
성공한 증명의 조각 길이 분포를 재본 적이 없다.
aime_1999_p11 의 핵심 조각(hsum_eq)은 100줄이 넘는다.
```

30이 적절한지, 문제 유형별로 달라야 하는지.

## 7.5 재귀 깊이와 스케치 품질

```
재귀 서브골 스케치가 전체의 73%
재방문 비율이 최상위(21%)보다 재귀(25%)에서 높다
```

깊이가 깊어질수록 문맥이 좁아져 분해 품질이 떨어지는가.
`max_depth_reached` 집계를 고쳐야 정량화할 수 있다(5.1).

# 부록 B — 스케치 품질 지표 탐색 (2026-09-04)

독립 연구를 위해 "좋은 스케치를 판별할 수 있는가"를 탐색한 기록이다.
**결론부터: 표면 지표는 전부 실패했고, 의존 구조 쪽에서만 신호가 보였다.**
다만 그 신호도 측정 방법에 결함이 있어 확정하지 못했다.

## B.1 라벨링 — 먼저 정정할 것

로그의 `No sorries found in proof sketch` 를 성공 신호로 쓰면 안 된다. 이것은
`_use_sketch_and_theorems_to_generate_proof` 뒤에 찍히는데, 그 함수는 스케치와
**아직 증명되지 않은** 서브골 정리들을 reasoner 에게 주고 조립하게 한다.
`sorry` 가 없다는 것은 조립된 텍스트가 완결됐다는 뜻이지 서브골이 닫혔다는 뜻이 아니다.
서브골 증명은 그 다음 단계(`_correct_theorems_from_sketch`)에서 일어난다.

```
잘못된 라벨   No sorries found  →  조립 성공 61.7%
올바른 라벨   Proof saved for problem X  →  최상위 스케치 462개 중 최종 성공 28개 (6.1%)
```

`Proof saved` 는 최상위 정리에만 찍히므로, 재귀 서브골 스케치의 성패는 이 방법으로
판정할 수 없다(전부 0%로 나옴). 재귀 쪽은 다른 마커가 필요하다.

## B.2 실패한 지표들

네 가지를 재봤고 전부 예측력이 없었다. 각각 왜 안 됐는지가 다음 시도에 중요하다.

### 크기 (have 개수, 줄 수)

```
같은 (로그, 정리) 안에서 성공·실패 스케치 비교 — 문제 난이도 통제됨
  have 개수 차이 중앙값   +0.0
  줄 수 차이 중앙값       +0.0
```
같은 문제에서 성공한 스케치와 실패한 스케치의 크기가 통계적으로 구분되지 않는다.

전체 분포를 보면 최상위와 재귀가 정반대 경향을 보여, 수준을 섞으면 방향이 뒤집힌다.

```
[최상위 462개]                    [재귀 1368개]
have  0-2   n=  11               have  0-2   n= 466
have  3-5   n=  89               have  3-5   n= 500
have  6-9   n= 179               have  6-9   n= 242
have 10-14  n= 138               have 10-14  n= 130
have 15+    n=  45               have 15+    n=  30
```

### 가정 개수 (자족성 대리지표)

서브골 정리문 2,581개에 결과 라벨(닫힘 2,230 / 못 닫음 351)을 붙여 쟀다.

```
가정 0개  n=  16   닫힘 100.0%
가정 1개  n= 105   닫힘  83.8%
가정 2개  n= 405   닫힘  90.6%
가정 3개  n= 510   닫힘  86.7%
가정 4개  n= 431   닫힘  88.4%
가정 5개  n= 334   닫힘  82.3%
가정 6개  n= 279   닫힘  82.4%
가정 7+개 n= 501   닫힘  86.0%
```

82~90% 사이를 오갈 뿐 단조 관계가 없다. **가정 개수는 자족성이 아니라 문제의 성격을**
**재고 있었다.** 성공 사례 `amc12a_2021_p8` 의 서브골은 가정 4개가 전부 점화식 정의라,
없으면 증명 자체가 불가능하다. 가정이 많은 것이 나쁜 것이 아니다.

### 재귀 깊이

서브골 이름은 부모 이름을 이어붙여 만들어지므로(`h_sub_hn_eq_hk_eq_hk_hn_문제이름`)
이름 속 `_h` 개수로 깊이를 가늠할 수 있다. `max_depth_reached` 가 항상 0이라 이 대리지표가 필요하다.

```
깊이 0  n=805  닫힘 93.3%
깊이 1  n=510  닫힘 87.3%
깊이 2  n=365  닫힘 89.9%
깊이 3  n=406  닫힘 76.6%
깊이 4  n=495  닫힘 79.8%
```

깊이 3부터 13%p 떨어진다. **그러나 이것은 선택 편향이다.** 재귀는 얕은 시도가 전부
실패했을 때만 일어난다(`_verify_and_correct_subgoal`, 1264행). 깊은 서브골은 정의상
어려운 가지에서만 생긴다. 깊이가 낮은 닫힘률을 만든 것이 아니라 어려운 문제가 깊이를 만들었다.

그리고 예측에 쓸 수 없다 — **한 정리에 대한 모든 스케치는 같은 깊이**이므로 후보 비교에
아무 정보를 주지 않는다.

### 전술 사전 실행 난이도 (`exact?` 등)

가설은 "자동 전술로 즉시 닫히는 서브골이 많으면 좋은 스케치"였다. **반증됐다.**

실패한 스케치(imo_2019_p1, R2)의 서브골에 전술을 직접 돌려본 결과:

```
서브골       exact?   simp_all   omega   aesop
h00          성공      ─         ─      ─
h_a0         성공      ─         ─      ─
h_b0         성공      성공       ─      성공
h_double     ─        ─         ─      ─
h_add        ─        ─         ─      ─
h_linear     ─        ─         ─      ─
```

절반이 즉시 닫힌다. 그런데 이 스케치는 14시간 쓰고 실패했다. 이유는 그 세 개가
**가설에 값을 대입한 것뿐**이기 때문이다.

```lean
have h00  : f (2*0) + 2*f 0 = f (f (0+0)) := by sorry   -- 이건 h 0 0
have h_a0 (b : ℤ) : f (2*0) + 2*f b = f (f (0+b)) := by sorry   -- h 0 b
have h_b0 (a : ℤ) : f (2*a) + 2*f 0 = f (f (a+0)) := by sorry   -- h a 0
```

**증명 진전이 0이다.** 이미 가진 것을 이름만 붙여 다시 쓴 것이라 쉬운 것이 당연하고,
쉬운 만큼 쓸모가 없다. 반대로 성공한 스케치(R1)의 서브골은 `exact?` 로 하나도 닫히지
않는다 — 그것들이 진짜 수학적 내용이기 때문이다.

**신호의 방향이 가설과 반대일 수 있다:** `exact?` 로 닫히면서 아무도 쓰지 않는 서브골은
군더더기다.

## B.3 의존 구조 — 유일하게 신호가 보인 곳

HILBERT 가 서브골을 독립 정리로 뽑을 때, 필요한 다른 서브골을 **가정으로 명시**한다.
이것이 의존 간선이다.

```lean
theorem h_c_eq (f : ℤ → ℤ) (h : ∀ a b, ...) :
    ∀ b, f (f b) = f 0 + 2 * f b                  -- 가정이 f, h 뿐

theorem h_f2a_eq (f : ℤ → ℤ) (h : ...)
    (h_c_eq : ∀ b, f (f b) = f 0 + 2 * f b)       -- ← h_c_eq 에 의존
    : ∀ a, f (2*a) = 2*f a - f 0

theorem h_cases (f : ℤ → ℤ) (h : ...)
    (h_c_eq : ...) (h_f2a_eq : ...)               -- ← 넷에 의존
    (h_add_eq : ...) (h_g_linear : ...)
    : (∀ z, f z = 0) ∨ ∃ c, ∀ z, f z = 2*z + c
```

같은 문제의 성공·실패 실행을 비교했다.

```
                  R1 (성공)    R2 (실패)
서브골              28개        69개
의존 간선           17개         8개
평균 의존           0.6         0.1
고립된 서브골        19개        57개 (83%)
```

R1 은 사슬을 이룬다. 앞의 결과를 뒤가 쌓아 올린다.

```
h_c_eq → h_f2a_eq → h_add_eq → h_g_linear → h_cases → h_cases'
         (h_c_eq)   (앞의 둘)   (앞의 셋)    (앞의 넷)
```

R2 는 흩어져 있다. `h00`, `h_a0`, `h_b0`(= `exact?` 로 즉시 닫히던 그 셋)이
**아무 데도 쓰이지 않는다.** 만들어놓고 버려진 조각이다.

이 지표는 앞의 넷과 성격이 다르다.

```
크기·가정 개수·깊이·난이도   개별 조각의 속성      →  전부 실패
의존 구조                    조각들 사이의 관계     →  신호 있음
```

## B.4 측정 방법의 결함 (다음에 반드시 고칠 것)

최종 증명 파일과 대조해보니 **가정 기반 추출이 의존을 크게 놓친다.**

```
imo_2019_p1 최종 증명의 정리      14개
본문 호출까지 세면 참조된 것       13개  (최상위 자신만 제외)
가정(binder)만 세면               7개  ← 절반을 놓침
```

놓치는 이유는 둘이다.

```
1. 가정으로 선언되지 않고 증명 본문에서만 호출되는 의존
2. reasoner 가 가정 이름을 다르게 붙이면 이름 일치가 깨짐
```

그런데 **본문 호출 기준은 성공한 경우에만 쓸 수 있다.** 실패한 스케치에는 최종 증명이
없기 때문이다. 성공·실패를 비교하려면 스케치 단계에서 관측 가능해야 한다.

남은 길: **스케치 본문의 `sorry` 바깥 구조를 파싱한다.**

```lean
have h_c_eq   : ... := by sorry
have h_f2a_eq : ... := by sorry
...
cases hk_cases with ...     ← 제어 흐름에 등장하는 이름
exact h_cases'              ← 최종 단계가 쓰는 이름
```

`sorry` 안쪽은 비어 있지만 바깥 구조(`exact`, `cases`, `refine`, `calc`, `simpa [...]`)에
나타나는 이름은 볼 수 있다. R2 의 `h00`, `h_a0`, `h_b0` 이 거기에도 안 나온다면 진짜 고립이다.

## B.5 아직 확인하지 못한 것

```
1,830개 전체에서 성립하는가
   지금 근거는 같은 문제의 두 실행 비교 하나뿐이다.

스케치 단계에서 관측 가능한 형태로 잴 수 있는가
   B.4 의 파싱을 구현해야 답이 나온다.

측정 도구의 편향 — 가장 시급하다
   가정 기반 추출이 의존의 절반을 놓친다(B.4). R2 가 R1 보다 본문 호출
   방식을 더 많이 썼다면 R2 를 부당하게 나쁘게 본 것이 된다.
   이것이 해결되지 않으면 어떤 비교도 성립하지 않는다.
```

### 서브골 수는 통제 대상이 아니다

처음에 "서브골 수를 통제해도 차이가 남는가"를 확인 항목으로 적었으나, 이는 잘못이다.

같은 문제의 여러 실행을 비교하면 **난이도가 설계상 고정**된다. 그러면 서브골 수의 차이는
난이도가 아니라 분해 선택에서 나온 것이므로, 교란 변수가 아니라 **매개 변수**다.
매개 변수를 통제하면 보려는 효과를 지운다 — "잘게 쪼개서 흩어졌다"가 바로 나쁜 분해의
내용인데 그것을 상수로 고정하는 셈이 된다.

그리고 애초에 기계적 편향이 크지 않다. `평균 의존 = 간선/노드` 는 연결된 구조라면
크기와 대체로 무관하다(사슬이든 별이든 간선 n-1개, 평균 ≈ 1).

실측(85개 (실행×문제) 조합):

```
노드  4-9   n=24   평균 의존 중앙값 1.00
노드 10-19  n=23                  1.08
노드 20-39  n=18                  0.61
노드 40+    n=20                  0.41

노드 수와 평균 의존의 상관계수  -0.177   ← 약하다
```

4~19개 구간에서 1.0 근처로 유지된다. 20개를 넘으면 떨어지는데, 이는 기계적 편향이라기보다
**서브골이 20개를 넘어간 실행은 실제로 분해가 발산한 것**으로 읽는 편이 자연스럽다
(`algebra_sum1onsqrt` 는 92개까지 불어났다). 즉 서브골 수 자체가 이미 나쁜 분해의 징후이므로
관측 대상이지 통제 대상이 아니다.

**이 확인은 분산 측정 실험이 끝난 뒤에 하는 것이 낫다.** 그때는 같은 조건에서 같은
문제를 3~5회 돌린 자료가 생기므로, 난이도를 통제한 성공·실패 비교가 가능해진다.
지금 자료는 조건이 제각각인 21개 실행이라 교란이 많다.

## C.3 사례 2 — algebra_sum1onsqrt: 중복 서브골

`∑_{k=2}^{10000} 1/√k < 198` 을 적분 비교로 증명하는 문제다. v4.16 에서 3회 돌렸고
1회 성공했다. **세 실행의 최상위 스케치를 나란히 놓으면 차이가 한눈에 보인다.**

### r3 (성공) — 4단계, 군더더기 없음

```lean
have h_antitone        : AntitoneOn (fun x => 1/√x) (Icc 1 10000) := by sorry
have h_integral_eq     : (∫ x in 1..10000, 1/√x) = 198 := by sorry
have h_sum_lt_integral : (∑ k in Icc 2 10000, 1/√k) < ∫ x in 1..10000, 1/√x := by sorry
have h_sum_lt_198      : (∑ k in Icc 2 10000, 1/√k) < 198 := by sorry
exact h_sum_lt_198
```

### r2 (실패) — 5단계, 중복 하나

```lean
have h_antitone
have h_sum_le_integral : ∑ ≤ ∫     ← 약한 버전
have h_integral_eq     : ∫ = 198
have h_strict          : ∑ < ∫     ← 강한 버전을 다시
have this              : ∑ < 198
```

`h_strict` 가 `h_sum_le_integral` 보다 강한 명제이므로 약한 쪽은 **논리적으로 불필요**하다.
그런데 만들어놓았으니 증명해야 한다.

### r1 (실패) — 6단계, 중복 둘

```lean
have h_antitone
have h_integral_eq     : ∫ = 2√10000 - 2√1   ← 중간 형태에서 멈춤
have h_integral_val    : ∫ = 198             ← 같은 적분을 다시
have h_sum_le_integral : ∑ ≤ ∫               ← 약한 버전
have h_strict          : ∑ < ∫               ← 강한 버전
have h_lt_198          : ∑ < 198
```

중복이 두 쌍이다. 적분 계산을 두 단계로 쪼갰고, 부등식도 두 버전을 만들었다.

### 중복 수가 재귀 부담과 정확히 대응한다

```
        중복 서브골   깊이1 재귀   reasoner 호출   결과
r3          0           2개         1373        성공
r2          1           3개         1502        실패 (한도 소진)
r1          2           4개         1502        실패 (한도 소진)
```

### 인과 사슬

```
최상위 스케치에서 ≤ 로 갈까 < 로 갈까
        ↓
h_strict 라는 별도 서브골이 생기느냐 마느냐
        ↓
그것을 재귀 분해하며 깊이 4까지 내려감
        ↓
응답이 길고 복잡해져 형식 오류 증가 (missing_tags 403 vs 278)
        ↓
reasoner 예산 1500 소진 → 실패
```

**중간 지표만 보면 원인을 놓친다.** 형식 재요청 횟수 차이(403 대 278)가 성패를 가른
것처럼 보이지만, 그것은 결과다. 원인은 최상위 스케치의 한 가지 선택이다.

## C.4 스케치는 실행마다 거의 겹치지 않는다

세 실행의 서브골 집합을 비교했다.

```
r1 ∩ r2   공통 3개 / 합집합 19개   자카드 0.16
r1 ∩ r3   공통 1개 / 합집합 21개   자카드 0.05
r2 ∩ r3   공통 1개 / 합집합 23개   자카드 0.04
```

**5% 도 겹치지 않는다.** 재귀 트리가 완전히 다르게 자란다. 같은 문제, 같은 조건,
같은 코드인데도 그렇다. seed 가 없고 temperature 0.6 이기 때문이다.

표면 지표로는 이 차이가 안 잡힌다.

```
깊이별 have 중앙값
  r1 (실패)   6, 4, 4, 3, 4
  r2 (실패)   4, 5, 3, 4, 4
  r3 (성공)   4, 5, 3, 4, 4      ← r2 와 완전히 동일
```

```
공통점   개별 조각의 속성이 아니라 조각들 사이의 관계
```

### 중복 검사는 구문만으로 상당 부분 가능하다

```
같은 좌변을 가진 서브골 쌍을 찾는다
   h_sum_le_integral 과 h_strict     좌변 동일, 부등호만 다름  (≤ vs <)
   h_integral_eq 과 h_integral_val   좌변 동일, 우변 형태만 다름

한쪽이 다른 쪽을 함의하면 약한 쪽은 불필요
   ∑ < ∫  ⟹  ∑ ≤ ∫

목표의 부등호 방향이 주 경로에 반영돼 있는가
   목표가 < 인데 주 경로가 ≤ 로 가면 엄격성 보조정리가 따로 필요해진다
```

이것은 부록 B 에서 실패한 표면 지표들(크기, 가정 개수, 깊이, 전술 난이도)과 성격이 다르다.
의존 구조(B.3)와 같은 계열 — **조각들이 이루는 논증 구조**를 본다.
